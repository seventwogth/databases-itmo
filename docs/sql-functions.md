# Poker API — SQL-функции

Договорённости:

* Диалект — **PostgreSQL**, функции на `PL/pgSQL`, расчёты комбинаций — на `SQL` с `IMMUTABLE`.
* Идентификаторы — `SERIAL`/`integer`, как в схеме.
* Пароль **не** попадает в БД: `register_user` принимает готовый `password_hash`.
* Auth Token в схеме не хранится — его держит и проверяет сервер (см. `api-schema.md`); БД отмечает только `Users.last_active`.
* Валидация бизнес-правил — внутри функций, через `RAISE EXCEPTION ... USING ERRCODE`, см. [Коды ошибок](#коды-ошибок).
* Кости передаются как `integer[]` — идентификаторы (`die_id`) или значения `1..6`.

Ссылочные действия из схемы: `Players → Users`, `Players → Game_sessions`, `Turns → Players`, `Dice → Turns` — `ON UPDATE CASCADE ON DELETE CASCADE`; `Turns → Combinations` — `ON UPDATE CASCADE ON DELETE SET NULL`.

**Ключевое следствие для функций:** ход адресуется через `player_id`, а не через пару (`session_id`, `user_id`) — `Players` имеет собственный суррогатный ключ, уникальный в пределах сессии (`AK1 = user_id + session_id`), и порядок хода хранится в `Players.turn_at`.

### DDL

```sql
CREATE TYPE session_status AS ENUM ('LOBBY_OPEN', 'IN_PROGRESS', 'FINISHED');

CREATE TABLE Users (
    user_id       serial PRIMARY KEY,
    login         varchar   NOT NULL UNIQUE,
    password_hash varchar   NOT NULL,
    last_active   timestamp
);

CREATE TABLE Game_sessions (
    session_id  serial PRIMARY KEY,
    started_at  timestamp      NOT NULL DEFAULT now(),
    status      session_status NOT NULL DEFAULT 'LOBBY_OPEN',
    turn_amount integer        NOT NULL CHECK (turn_amount >= 1)
);

CREATE TABLE Combinations (
    combo_id serial PRIMARY KEY,
    name     varchar NOT NULL UNIQUE,
    points   integer NOT NULL
);

CREATE TABLE Players (
    player_id    serial PRIMARY KEY,
    user_id      integer NOT NULL REFERENCES Users (user_id)
                         ON UPDATE CASCADE ON DELETE CASCADE,
    session_id   integer NOT NULL REFERENCES Game_sessions (session_id)
                         ON UPDATE CASCADE ON DELETE CASCADE,
    turn_at      integer NOT NULL,
    total_points integer NOT NULL DEFAULT 0,
    UNIQUE (user_id, session_id),
    UNIQUE (session_id, turn_at) DEFERRABLE INITIALLY DEFERRED
);

CREATE TABLE Turns (
    turn_id     serial PRIMARY KEY,
    player_id   integer NOT NULL REFERENCES Players (player_id)
                        ON UPDATE CASCADE ON DELETE CASCADE,
    combo_id    integer REFERENCES Combinations (combo_id)
                        ON UPDATE CASCADE ON DELETE SET NULL,
    turn_number integer NOT NULL,
    throw_number integer NOT NULL,
    is_closed   boolean NOT NULL DEFAULT FALSE,
    UNIQUE (player_id, turn_number)
);

CREATE TABLE Dice (
    die_id   serial PRIMARY KEY,
    turn_id  integer NOT NULL REFERENCES Turns (turn_id)
                     ON UPDATE CASCADE ON DELETE CASCADE,
    value    integer NOT NULL,
    is_fixed boolean NOT NULL DEFAULT FALSE
);
```

`CHECK`-ограничения на `Dice.value` и `Turns.throw_number` задаются в разделе 6 (`trg_dice_value_range`, `trg_turns_throw_range`).

### Расхождения со схемой, которые закрывают функции

* В `Turns` добавлена колонка `is_closed boolean NOT NULL DEFAULT FALSE`. По схеме ход закрывается выбором комбинации (`combo_id IS NOT NULL`), но ход, пропущенный после третьего броска, тоже без комбинации — отличить его от текущего хода без флага нельзя. Флаг ставят `finish_turn` и `skip_turn`.
* Ограничение `UNIQUE (session_id, turn_at)` (`AK2`) объявлено `DEFERRABLE INITIALLY DEFERRED`, иначе перенумерация `turn_at` в `leave_lobby` и `assign_turn_at` упирается в уникальность посреди `UPDATE`.

| `P0103` | `lobby_full` | В лобби уже 4 игрока | 409 |
| `P0104` | `already_joined` | Пользователь уже в этом лобби | 409 |
